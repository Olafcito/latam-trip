# Shared trip data

The repo no longer contains a data snapshot. Supabase is the single source of truth for researched data, planned trip versions, tasks, documents and the inbox.

## Read and write

Run commands from the repository root:

```bash
python -I -X utf8 plugin/scripts/tripdb.py --root . --help
python -I -X utf8 plugin/scripts/tripdb.py --root . status
python -I -X utf8 plugin/scripts/tripdb.py --root . query trips_latest
python -I -X utf8 plugin/scripts/tripdb.py --root . doc-get trip.json
```

`tripdb query TABLE` reads table rows. `tripdb doc-get NAME` reads a stored document, and `tripdb file NAME` reads a worker-built app file. Use the matching `tripdb` write command for changes. `tripdb check` validates database state. Never edit a second local source copy or write directly to Supabase outside the supported commands.

Planned trips live in the `trips` table. `tripdb save-trip FILE` saves a new version and prints its id. The planner opens it at `/?trip=<id>` and syncs it across signed-in devices.

The app's built map and research files live in the public Supabase `web` bucket. A scheduled worker rebuilds and publishes them after data changes. Worker health is shown by `tripdb status`; worker deployment is `bash infra/deploy.sh --enable-schedules`.

## Owners

Every private table (trips, quotes, tasks, inbox, task_log, agent_usage, bookings, lodgings and their rooms and prices) has an `owner_id`, and `admins` holds the one admin's user id. The secret key bypasses row level security, so `tripdb` and the worker name `owner_id=eq.<admin id>` on every read, change and delete, with the id read from `admins` at run time and never from a file. The connector holds no secret key (TECH-010). Each call goes as the signed in person, with the publishable key as `apikey` and their own token as bearer, so row level security keeps it to their rows, and it names their own user id as `owner_id` on every call. The connector reaches no service table. `stays` became a catalogue table in migration 0033, so `list_stay` and `get_stay` find its rows, and only the admin's token writes the catalogue. `add_quotes` runs as the caller and stores the caller's own id as `owner_id`, and the airport codes a quote names are added as stubs by `add_airport_stubs`, which only inserts a missing three letter code. A write names the owner too, and one that does not lands on the admin. `tripdb query` refuses a test on `owner_id`. A person's own documents (lists.json, trip.json, mcp_trash.json, web_trips, way_id_map, unresolved_journeys, current_plan) live in `user_documents` by `(owner_id, name)`. The shared ones, such as `cutover_done`, stay in `documents`. The worker pull reads the catalogue whole and the admin's quotes, trips and usage only, and does not pull `task_log`, so no `task_log.json` is built into the public bucket. The morning rates run prices the admin's places only. Lodging ids are derived from the owner as well as the place and name, and the connector finds a stored lodging among the caller's own by place and name before it trusts a derived id. Booking files are stored under `<owner id>/<booking id>/` in the private `bookings` bucket.

Migration 0027 gave every row of before to the admin and turned on row level security per person. A signed in person reads and writes only the rows whose `owner_id` is their own user id, in the private tables, `user_documents` and `user_profiles` (one row of `home_airport`, `currency`, `max_hours`, `travel_style` and `rules` per person, read and written through the connector's `get_profile` and `update_profile`). The catalogue (airports, places, connections, profiles, place_images, experiences, experience_images and documents) is read by every signed in person and written by the admin only, and `derive_state` is read by every signed in person and written by none. `stays` joined the catalogue in migration 0033. The service tables (`admins`, `inbox_tokens`, `leases`, `derived_options`, `site_calls`, `hostelworld_cities`, `task_runner`, `owner_limits`) have no client policy. `public.is_admin()` says whether the caller is the admin and `public.admin_id()` gives the admin's id, refusing unless there is exactly one admin. `public.is_owner()` is kept as a name for `is_admin()`. The keys that were unique across the data are unique per owner: a trip is `(owner_id, id, version)`, a quote's `quote_id`, the stay_picks task of a place and dates, and a room's `(lodging_id, site, site_id)`. A lodging, a room, a price and a booking are keyed `(owner_id, id)`, so an id another person uses is as free as a fresh one. Migration 0031 keys `tasks` and `inbox` the same way and `task_log` as `(owner_id, seq)`, so an explicit id that another person holds is answered as a fresh id is. The identity counters stay shared, so an id only tells a person how many rows exist in all. A room points at its lodging and a price at its room by `(owner_id, id)`, so neither can sit under another person's row. `bookings.lodging_id`, `bookings.room_id` and a task's `lodging_id` are plain values, and the stay_details functions (`close_stay_details(lodging, owner)`, `stay_details_complete` and `stay_details_dates`, which take the owner first) match them on the owner. An inbox token carries the owner its submissions land on. `owner_limits` holds the limits per person (2000 rows per private table, 100 tasks a day, 200 MB of booking files and 60 connector writes a minute), which nothing enforces yet. The task runner is woken for the admin's tasks only. A write to `quotes`, `task_log`, `inbox` or `user_documents` marks the build dirty only when it touches a row of the admin's, so another person's write never starts a build.

Migration 0028 limits the `bookings` bucket to the folder named by the caller's user id. Files stored before it live at `<booking id>/<file>`, which the admin alone can still reach, and only under a folder named by one of the admin's own bookings (`public.bookings_file_allowed`). `python -I -X utf8 supabase/move_booking_files.py --apply`, run once from the PC after the release, moves the files of the folders named by the admin's booking ids to `<admin id>/<booking id>/<file>` and updates the bookings rows. Any other folder stays where it is. It works one booking at a time, copying its files, pointing its row at the copies and then removing the old files, and stops at the first failure, so every booking names files that exist and a second run carries on. It prints counts only, and without `--apply` it shows what would move. A later migration drops the admin's access to the old paths.

## Backups and safety

The scheduled worker stores private backups in `latam-trip-backups`. Use `tripdb dump` and `tripdb restore` only for an explicitly reviewed recovery. A restore can replace project tables, so verify the target and archive before running `--wipe`. Never use test reset helpers against the live project.

The `read-booking` edge function (`supabase/functions/read-booking`) reads a booking confirmation for Add booking. Any signed in person may call it up to a number of reads a month, counted in `read_booking_usage` (migration 0029), which no client reads. It touches no other table. Its README has the deploy commands.

## Places to stay and live rates

`lodgings`, `lodging_rooms` and `lodging_prices` are per person and never in a built file. A room keeps `site` and `site_id`, where it was read from and its id there, and a `photo`. A price keeps `available`, the beds (a dorm) or rooms (a private) left when it was seen. The `stay-rates` edge function (`supabase/functions/stay-rates`) reads a place's rooms and prices from Hostelworld for a date range and writes them to these tables, when the planner opens a place with a Hostelworld link, when a Hostelworld link is pasted to add a place, and each morning from the worker's `rates` action for every place and dates with a Hostelworld price ahead. Its README has the deploy commands and the worker key. A trigger on `lodgings` (migrations 0022 and 0024) queues one `stay_details` task for each Booking.com or Airbnb place that is added and not hidden, which Simon's PC does by the `add-lodging` skill: for Booking.com it reads the hotel page and `tripdb lodging-details FILE` stores every room, its photo and prices, and the place photos. An Airbnb listing is read by a browser worker that writes its price and photos through the connector. A `stay_details` task closes by the data: triggers on `lodgings`, `lodging_rooms` and `lodging_prices` (migration 0025) set it `done` once the place has photos, a room and a price for the dates on every room, with the counts and dates as its result and no price. The dates are the task's, else the dates priced on every room, the most recently seen when several are (migration 0026). A `stay_prices` task closes the same way (migration 0030) once every room named in its `room_ids` has a price for its dates seen after the task was queued. A failed task stays failed. The connector's `add_lodging_price` and `tripdb` check `available` against 0 and `site` against the known sites.

## Hostelworld gate and cities

`site_calls` and `hostelworld_cities` are read and written only by the `stay-rates` edge function with the service role. Row level security is on with no policies, so no signed in client sees them (`supabase/migrations/0020_hostelworld_search.sql`, TECH-004).

- `site_calls` holds one row per Hostelworld request in the last minute. The function `take_site_call(site, per_minute)` takes a turn: it returns 0 and counts the call when there is room, else the seconds to wait. Every Hostelworld request of the function passes it, 30 a minute across the planner, the worker and the search. Rows older than a minute are deleted on the next turn.
- `hostelworld_cities` remembers the Hostelworld city of a map place, `place_id` to `city_id` and `city`, with `checked_at`. A null `city_id` means Hostelworld has no city by that name, and the lookup is tried again after 30 days.
