# Claude tasks: the checklist between the app and Claude

The app never runs searches itself. It writes a task to Supabase, and Claude does the work with the plugin (Sonnet browser workers for prices, web research for experiences and places), then writes the results back to Supabase.

## How a task is handed over

The app inserts one row into the `tasks` table. Its `data` column holds the task JSON below, `title` is `[<type>] <short summary>`, and `trip_id` and `trip_version` say which trip it was asked from. A `question`, `lists_update`, `experience_research`, `stay_prices` or `refresh` of experiences starts Claude by itself within about a minute (`docs/task-runner.md`). That run takes tasks with the connector's `claim_task`, which checks the fields below and refuses a task that lacks them, and it prices stays on Booking.com only. The rest wait until Simon tells Claude "check the checklist", and Claude runs the `trip-checklist` skill, which works through every open row.

Claude uses `tasks.py`: `list` shows the open and working rows, `show N` prints the task JSON, `start N` sets `working`, and `done N SUMMARY_FILE` writes the result, sets `done` and logs it with `tripdb log-task`. The result is markdown and shows in the app next to the button within seconds.

Example `data`:

    {"type": "stay_prices", "lodging_id": "<lodging id>", "room_ids": ["<room id>", "<room id>"], "check_in": "2026-12-10", "check_out": "2026-12-14", "note": "Dorm and private for 10 to 14 Dec."}

## Task types

All tasks may also carry `"note"` (free text from Simon) and `"from"` (`"app"`).

| type | fields | what Claude does |
|---|---|---|
| `flight_prices` | `legs`: list of `{from, to, date, flex_days}` (IATA codes, ISO dates, `flex_days` 0 to 3 = also search that many days before and after); optional `name` for a self-built itinerary; optional `all_flights` (true) to keep every flight on all of those days | One leg = one-way, two legs back to the start = return, otherwise open jaw or multi-city. A self-built itinerary (for example CPH > CUN, CUN > GDL, GDL > GUA, VVI > CPH) is searched three ways: the legs touching Europe as one combined ticket from and back to Copenhagen, each regional leg as a one-way, and the whole thing as one multi-city search when it has 6 legs or fewer. With `all_flights`, which the app's flight sheet sends, every date is a full search and every flight is kept instead of the few that differ most, so the planner's day lists fill up. Workers save results with `tripdb` and the worker publishes the next build. |
| `stay_prices` | `lodging_id` (a lodging that exists), `room_ids` (its rooms to price), `check_in`, `check_out` | `stay-price-worker` reads the lodging with the connector's `get_lodging` and prices each room for the dates on the lodging's own links (Booking.com through its connector with 1 adult, DKK and `user_country_code` dk, Hostelworld in the browser). It writes one `lodging_prices` row per room with `add_lodging_price`, in DKK, with the site, link, refundable and last day to cancel. A price task writes prices only: it never adds a lodging or a room, and never writes the old `stays` table, which `tripdb add-stays` keeps closed. `tasks.py list` shows a task without these fields as a bad task. |
| `experience_research` | `experience` (id) or `place` + `question`; optional `dates` | Web research; the experience row is saved to Supabase with `tripdb add-experience` or `update-experience`, including price, season, Dec/Jan conditions, booking and sources, and `researched: true`. A new experience gets a new row. |
| `place_research` | `name`, `country`, optional `question` | `place-profiler` and `network-researcher`: a new map place with profile, things to do and connections. |
| `lists_update` | `list` (id), `add` and `remove`: lists of `{type: place or experience, id, note}` | Applied to the Supabase lists document with `tripdb list-add` and `list-remove`. |
| `question` | `text` | Answered in the result of the row. |
| `booking` | `leg`: `{kind, from, to, day}` (`kind` is `flight`, `bus` or `boat`, `from` and `to` are the codes or place ids of the leg's two ends, `day` the ISO day it leaves) and `text`, what Simon wrote about the booking, such as where the confirmation mail is | The app no longer sends this task, since Add booking reads the confirmation itself through the `read-booking` function (TECH-001). The row stays for tasks already in the table. It was sent from Ask Claude in the Mark as booked form. Claude first calls `list_booking` with `from`, `to` and `day`, so nothing is booked twice, and updates a booking that is there with `update_booking`. Otherwise it reads the confirmation Simon points to and adds one row per leg with `add_booking` with what it holds: reference, seller, price paid in kroner, times, the flights inside, bags, refundable and changeable with their last days, the link and notes. A ticket over several legs shares `reference` and `ticket`, with the price on the first row and 0 on the others. Files go on the row with `attach_booking_file`, up to 4 MB as base64, or `attach_booking_upload` for a larger one. The result names the legs booked, never the reference or the price, since the result shows in the app. `tasks.py done` logs only the task's type and leg to the public `task_log`, never its text. The logged summary is the word Booked and the outputs are empty, whatever the result file says. `tripdb log-task` and `build_web_data` do the same again. |
| `refresh` | `scope`: `all`, `flights`, `stays` or `experiences`, an optional `item` (a connection pair, place id, experience id or itinerary name) and `older_than_days` (default 3) | Re-runs the searches behind everything in scope that was last checked more than `older_than_days` ago. For flights that is the top whole trips and long-haul tickets, the regional pairs they use and any self-built itineraries. For stays it is the rooms and dates of the latest prices of each lodging. For experiences it is the researched ones. The app's update button sends this. |
| `import_quotes` | `rows`: price rows in the worker format with `source: "momondo-manual"`, `observed_at` in UTC and, for a saved trip, `trip_name`. Also `count`, `legs`, `page` (the Momondo address), `from: "userscript"` and optional `trip_name`. | Writes the rows unchanged to the Supabase inbox as one row of status `new`. The scheduled worker ingests it. The userscript normally submits directly through `submit_inbox`. The prices show in the app as saved by you. |
| `fix_parser` | `parser_version`, `reason` (for example `3 of 14 rows have empty legs`), `action` (`save_prices` or `save_trip`), `view`, `page`, `legs`, `dialog_text`, `dialog_chars` and optional `dialog_cut` | Reproduces the failure by running `parseDlg` from `momondo_crawler.js` on `dialog_text`, fixes the parser and bumps `PARSER_VERSION`. Saves the text as a new fixture with an expected file, runs `node plugin/userscripts/build.js` and `node --test "plugin/userscripts/**/*.test.js"`, then pushes. Tampermonkey updates the script by itself. Reports the new parser version in the result. |

## When a task is done

Claude writes the result with `tasks.py done`, which marks the row `done`, stores the markdown in `result` (a short table with prices, local clock times and sources), and logs it in `task_log` with `tripdb log-task` (`issue` holds the task id, `type`, `done_at`, `summary`, `outputs`). The worker publishes the next built data snapshot.

## Last checked
