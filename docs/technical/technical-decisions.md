# Technical decisions

Ids never change. Status is Proposed, Accepted, Implemented or Reconsidered. The plan author proposes, Simon accepts. A decision cites the FEAT or plan it came from, and a plan cites the TECH ids it relies on.

Format of an entry:

## TECH-NNN Short name

- **Decision.** What was chosen.
- **Reasoning.** Why, and what was weighed against it.
- **Applies to.** Files, tables or services.
- **Source.** The FEAT, plan or spec path.
- **Date.** **Status.**

## TECH-001 Reading bookings with the Claude API in an edge function

- **Decision.** Add booking reads a confirmation (a PDF, a screenshot, a saved .eml or pasted mail text) in the Supabase edge function `read-booking`. The planner sends the files inline as base64 with the leg and the text. The function lets in any signed in person, read from the session JWT, up to `READ_BOOKING_MONTHLY_CAP` reads a month (default 30, counted by `take_read_booking` in `read_booking_usage`, migration 0029), answers `429 monthly_cap` past it, and asks the Claude Messages API for one forced `booking` tool call and returns its input. It reads with Haiku (`READ_BOOKING_MODEL`, default `claude-haiku-5-5`) and reads once more with Sonnet (`READ_BOOKING_FALLBACK`, default `claude-sonnet-5-5`) only when the first answer misses the reference, the price or a leg's departure. It stores no file, keeps only the monthly count and logs nothing of the content. The form opens filled in, and the person checks and saves.
- **Reasoning.** The app has no mailbox access, so the confirmation has to come to it. Gmail API access was rejected because a public app reading mail needs Google's restricted scope review. A pasted Gmail link is kept as the booking's mail link and nothing more. The function holds the Anthropic key as a Supabase secret, so no key reaches the browser. With other people signed in (FEAT-006), the monthly cap per person keeps the spend bounded, and the count lives in the database because the function's instances share nothing. Forwarding mail to an address of the app is the later step for other users. Haiku reads a plain confirmation well at a fraction of the cost, and the three fields it is checked on are the ones a booking is useless without, so Sonnet is paid for only when they are missing.
- **Applies to.** `supabase/functions/read-booking/`, `supabase/migrations/0029_read_booking_cap.sql`, `planner/src/lib/readBooking.ts`, the `ANTHROPIC_API_KEY`, `READ_BOOKING_MODEL`, `READ_BOOKING_FALLBACK` and `READ_BOOKING_MONTHLY_CAP` function secrets.
- **Source.** The Add booking task of the `feat/add-booking` worktree.
- **Date.** 2026-11-05. **Status.** Implemented.

Browser tasks stay on Simon's machine.

## TECH-003 Live rates from Hostelworld through an edge function

- **Decision.** The Supabase edge function `stay-rates` reads a place's rooms and prices for a date range from Hostelworld's own unauthenticated JSON endpoints (`legacy-hwapi-service/2.2/properties/{id}/` and `.../availability/`), with a browser like user agent, one guest and DKK. It writes the rooms to `lodging_rooms`, remembering the site and the room's id there, and one `lodging_prices` row per room with the beds or rooms left. The planner calls it when a place with a Hostelworld link is opened and shows the stored rows first, the live ones through realtime. A pasted link adds the place through the same function. The build worker calls it at 05:00 UTC for every place and dates with a Hostelworld price ahead, with the key it already holds, which the function knows as the `STAY_RATES_WORKER_KEY` secret. The function is deployed with `--no-verify-jwt` because that key is not a JWT, and it checks the caller itself: any signed in person from the session JWT, or the worker key. It writes with the service role and names the owner on every read and write, the caller's own id, or the admin's for the worker, so each person's places stay their own (FEAT-006).
- **Reasoning.** Simon needs prices now to book, and neither Booking.com nor Hostelworld gives an API without a partner contract. Hostelworld's site reads from an endpoint that answers a plain fetch, so a function in Supabase can read it without a browser, a key or Simon's PC, which the task runner's Hostelworld step needed. Booking.com was weighed and left for later: its pages give a bot challenge to a plain fetch, its connector gives one cheapest total per property with no rooms, and the data search engines index of it is static page content, not dated prices. Keeping the reading in the function rather than the worker means the planner and the worker share one path and one write rule. The endpoint is unofficial, so the function fails soft and the age mark shows a price going stale.
- **Applies to.** `supabase/functions/stay-rates/`, `supabase/migrations/0019_lodging_live_rates.sql`, `supabase/migrations/0027_owners.sql`, `planner/src/lib/stayRates.ts`, `infra/worker/rates.py`, the `rates` schedule in `infra/deploy.sh`, the `STAY_RATES_WORKER_KEY` function secret.
- **Source.** `docs/product/features/FEAT-002-hostelworld-live-rates.md`.
- **Date.** 2026-11-05. **Status.** Implemented.

## TECH-004 Finding the top hostels of a stop through Hostelworld's city list

- **Decision.** The `stay-rates` edge function takes a search request for a map place and dates. It finds the place's Hostelworld city by name through the unauthenticated `suggestions/` endpoint, once, and remembers it in `hostelworld_cities` for 30 days, a miss included. It reads every property of that city for the dates from the city list endpoint `legacy-hwapi-service/2.2/cities/{id}/properties/`, which Hostelworld's own search page uses. That endpoint needs the `api-key` header of Hostelworld's public web app, which the function holds as the `HOSTELWORLD_WEB_KEY` secret, never in the repo. It keeps the hostels within 40 km of the map place, ranks those rated 8.0 or more by number of ratings and fills from the rest by number of ratings, then adds and prices the top ones through the same path as a pasted link, with `added_by` claude. Every Hostelworld request of the function, the planner's, the worker's and the search's alike, first takes a turn from `public.take_site_call('hostelworld', 30)`, a gate in Postgres that counts the calls of the last minute under an advisory lock. A call waits its turn, gives up after about 45 seconds with `429` and `retry_after`, and makes no call when the gate cannot be asked. A pasted link to a place more than 60 km from the stop is refused, so a hostel cannot land at the wrong stop as Dreamer Beach Club of San Andres did at Cartagena.
- **Reasoning.** Simon's limit is 30 Hostelworld requests a minute, and the callers run in separate edge function instances, so the count has to live in one place they all reach, the database. Failing closed keeps the limit when the database is in trouble. The number of ratings is the plainest measure of popularity that the list gives, and the rating floor keeps a busy but poor place from the top. Hostelworld's own list order mixes in promoted places, so it was not used. The 40 km circle drops places a city list carries from nearby towns and islands. The city list is unofficial like the endpoints of TECH-003, so the search fails soft and what is stored stays.
- **Applies to.** `supabase/functions/stay-rates/`, `supabase/migrations/0020_hostelworld_search.sql`, the `HOSTELWORLD_WEB_KEY` function secret.
- **Source.** `docs/product/features/FEAT-003-hostelworld-city-search.md`.
- **Date.** 2026-11-05. **Status.** Implemented.

## TECH-005 Booking.com page details come from a headless read on Simon's PC through a queued stay_details task

- **Decision.** The task runner adds a Booking.com place through the connector with one room, the cheapest shown, and no photos, because the connector gives nothing more. A trigger on `public.lodgings` (migration 0022) then queues one open `stay_details` task for each Booking.com place that is added and not hidden, unless one is already open or working for it. The type is not a cloud type, so no run starts for it. On Simon's PC the checklist run reads the hotel page with `plugin/scripts/booking/read.mjs` in a headless browser, and `tripdb lodging-details FILE` stores every room, the room photos, the price of each room for the dates and the place photos. A room is matched to a stored one by its Booking.com room id, else by name among the rooms without an id, so the cheapest room the runner stored is adopted and not doubled. No room is deleted, and photos are replaced only when the read found some. If the headless read is blocked, a Sonnet subagent reads the same page in Simon's Chrome through the Chrome plugin and writes the same JSON. The read is read only: it never clicks a consent, signs in or solves a bot check.
- **Reasoning.** Booking.com gives a bot challenge to a plain fetch from a server and to datacenter browsers, as TECH-002 and TECH-003 found, so the page can only be read from Simon's own machine. A queued task keeps the work visible on the checklist and survives a PC that is off, where reading at add time could not. Keeping the type out of the cloud list leaves `task_runs_in_cloud` as 0021 left it.
- **Applies to.** `supabase/migrations/0022_stay_details_task.sql`, `plugin/scripts/tripdb.py` (`lodging-details`), `plugin/scripts/booking/`, `plugin/skills/trip-checklist/`, `docs/claude-tasks.md`.
- **Source.** Simon's request on 2026-11-05 that a place added from Booking.com gets its rooms found after it is added.
- **Date.** 2026-11-05. **Status.** Accepted.

## TECH-007 Task status follows the data

- **Decision.** A `stay_details` task is closed by the database when its lodging is complete: photos, at least one room and a price for the dates on every room. The dates are the task's `check_in` and `check_out`, else the dates that have a price on every room, the most recently seen when several do, and no such dates means not complete. Triggers on `lodgings` (photos), `lodging_rooms` and `lodging_prices` (migrations 0025 and 0026) call `close_stay_details` for the one lodging, and the migration ends by closing every task that was already complete. Only an open or working task closes, a failed one is never touched. The result is `Closed by the data: N photos, M rooms, each priced for YYYY-MM-DD to YYYY-MM-DD.` with no price. `tasks.py done` on a task that is already done keeps the status and result and still logs. Migration 0030 does the same for `stay_prices`: a task is complete when every room in its `room_ids` is a room of its lodging and has a price for its `check_in` and `check_out` seen after the task was queued, so a price that was already there does not close a fresh task. The result is `Closed by the data: N rooms priced for YYYY-MM-DD to YYYY-MM-DD.` A task with no dates, no rooms or a missing room never closes. `finish_task` on a task the data closed keeps its result and still logs.
- **Reasoning.** A chat session that adds a place and fills it in the same turn left its `stay_details` task open, so the PC read the page again and the checklist showed work that was done. The data is the truth about whether a place is complete, so the status follows it and no one has to remember to close the task. The queued tasks carry no dates. 0025 took those of the latest price, but a newer price for a longer stay on only some rooms then hid a place fully priced for its stop, so 0026 looks for dates priced on every room. The PC closing a task the data already closed must not fail or reopen it.
- **Applies to.** `supabase/migrations/0025_task_close_by_data.sql`, `0030_stay_prices_close.sql`, `supabase/test_task_close.py`, `supabase/migrate.py`, `plugin/skills/trip-checklist/scripts/tasks.py`, `plugin/skills/add-lodging/SKILL.md`, `docs/claude-tasks.md`, `data/README.md`.
- **Source.** `docs/superpowers/plans/2026-11-06-feat-006-many-users.md`, task 1.1 and review focus 4.
- **Date.** 2026-11-06. **Status.** Proposed.

## TECH-008 Release pipeline

- **Decision.** GitHub Actions tests and releases the repo. `.github/workflows/test.yml` runs on every pull request, on a push to any branch but `main` and as a reusable workflow. It has `permissions: contents: read`, no secret, no `id-token` and never `pull_request_target`, so a pull request from a fork runs it safely. Its jobs are python (the tripdb, `tasks.py`, connector, worker and cutover tests), node (typecheck and tests of `web` and `planner`) and database. The database job starts a local Supabase stack with `supabase/local_up.sh`, which pins the Supabase CLI to an exact version, runs from `supabase/local` with no migrations of its own and applies `supabase/migrations/` with `migrate.py --db-url`, then runs `supabase/test_task_close.py` and `plugin/scripts/test_db_functions.py` there and fails on a skipped test. `.github/workflows/release.yml` runs on a push to `main` and on `workflow_dispatch`. It calls the test workflow, and only when every test passes two jobs run in turn in the GitHub environment `release`, which only `main` may use and which holds `SUPABASE_PASSWORD`, `SUPABASE_URL` and `AWS_RELEASE_ROLE_ARN`. The job `migrate` applies new migrations with `migrate.py` and has no `id-token`. The job `connector` never sees the database password. It takes the role `latam-trip-release` through GitHub's OIDC, with the account id masked in the public logs, and runs `infra/mcp/deploy.sh --code-only`, which first stops when the function's configuration lacks a variable the code reads, then uploads the connector zip, updates the Lambda code, waits for the update and checks that `POST /mcp` without a bearer answers 401 with `resource_metadata`. When the release has succeeded on a push to `main`, `site.yml` builds and uploads the planner, so the planner never runs ahead of the schema. The role's trust names the subject `<prefix>:environment:release` with `StringEquals` and no wildcard. The repo uses GitHub's immutable subject, so the prefix carries the owner and repo ids, and `setup.sh` reads it from the repo's OIDC settings rather than writing it into the template, and its policy allows putting and reading `function-*` objects in the deploy bucket and updating and reading the one function, nothing else. The connector's own role may read the two exact SSM parameters it needs, both plain String, and has no `kms:Decrypt` (TECH-010). The role and the environment are made from the PC with `infra/release/setup.sh`, which prints every command before it runs it, fills the placeholders of `trust-policy.json` and `role-policy.json` into a temp folder outside the repo and refuses when the repo customizes its OIDC subject. Every third party action is pinned to a full commit SHA, and uv, psycopg and the connector's packages to exact versions.
- **Reasoning.** A release is a push to `main` (FEAT-006), so no one runs migrations or deploys by hand. The repo is public, so the test workflow can hold nothing worth stealing, and the deploy secrets sit in an environment that a branch or a fork cannot reach. The role cannot use CloudFormation, because `CAPABILITY_NAMED_IAM` could create a role and a role that creates roles can make itself an admin. A template change therefore stays a full `deploy.sh` that Simon runs from the PC, which also brings the stack's `CodeS3Key` back in line with the code the release uploaded. Edge function deploys stay on the PC too, since a Supabase access token in CI could change every project setting. A Supabase branch costs a paid plan, so migrations are tested on a local stack, and the stack runs without the CLI's migrations because two files share the number 0024. Approval before a deploy was weighed and left out by Simon on 2026-11-06. A ruleset on `.github/` was to take its place. GitHub refuses push rules on a public repo ("Source public repos cannot have push rules"), and a branch ruleset can only require a pull request for every path, which Simon cannot approve as the author on his only account. So for now `main` has a branch ruleset that forbids force pushes and deletion, with no bypass, and the guard waits for a second GitHub account that Claude pushes as, with write access. Then `main` requires a pull request, `.github/CODEOWNERS` names Simon for `/.github/`, a code owner review is required, no approval is needed elsewhere and Simon as admin bypasses. Claude merges its own pull requests, and one that touches `.github/` waits for Simon. Until then the guard is the environment's branch policy, the role's narrow policy and the split jobs (plan finding 6). The same account serves the fork test of finding 7 and the live run.
- **Applies to.** `.github/workflows/test.yml`, `.github/workflows/release.yml`, `supabase/local/`, `supabase/local_up.sh`, `supabase/migrate.py`, `plugin/scripts/test_db_functions.py`, `infra/mcp/deploy.sh`, `infra/mcp/template.yaml`, `infra/release/`.
- **Source.** `docs/product/features/FEAT-006-many-users.md` section 7, Release pipeline, and `docs/superpowers/plans/2026-11-06-feat-006-many-users.md`, phase 1b.
- **Date.** 2026-11-06. **Status.** Implemented. The first release ran on 2026-11-06 (tests, `migrate: done`, connector updated, smoke 401), and a dispatch from a branch was refused by the environment.

## TECH-009 Ownership in the database

- **Decision.** Every private table carries `owner_id uuid not null`, defaulting to `coalesce(auth.uid(), public.admin_id())`, so a write with the secret key and no owner lands on the admin. Row level security lets a signed in person read and write only the rows with their own id, in the private tables, `user_documents` and `user_profiles`. The catalogue is read by every signed in person and written by the admin only. `owners` became `admins`, `public.is_admin()` and `public.admin_id()` answer for it, and `public.is_owner()` stays as a name for `is_admin()` until the callers move. Keys that were unique across the data are unique per owner. A lodging, a room, a price and a booking are keyed `(owner_id, id)`, so a write never learns that another person uses an id, and migration 0031 keys `tasks` and `inbox` `(owner_id, id)` and `task_log` `(owner_id, seq)` for the same reason, with the stay_details close matching a task by owner and id, and a room or a price points at its parent by `(owner_id, id)`, so nothing can hang under another person's row. Per person documents moved from `documents` to `user_documents (owner_id, name)`. Booking files live under `<owner id>/` in the private bucket. The secret key bypasses row level security, so `tripdb`, the worker and the connector name the admin's id on every read, change and delete, read from `admins` at run time and never from a file. The worker builds the public bucket from the catalogue and the admin's rows only, and never from `task_log`. Only a write to the admin's rows of `quotes`, `task_log`, `inbox` and `user_documents` marks the build dirty. `derive_state` is readable by every signed in person, so it holds counts and stage names, never trip ids or row text. No private table is in the realtime publication, and a change reaches its owner on a private topic of their own (TECH-012). `stay-rates` and `read-booking` read the caller from the JWT and write with the caller's id. `read-booking` counts each read per person and month with `take_read_booking`, with the cap in the secret `READ_BOOKING_MONTHLY_CAP` (default 30), and answers 429 `monthly_cap` past it. The admin has the same cap. Migration 0035 holds `owner_limits` in the database: a statement level trigger on each private table counts the owner's rows after an insert, under a lock per table and owner, and refuses past `rows_in_<table>` or else `rows_per_private_table`, and on `tasks` past `tasks_per_day`, counted per owner and UTC day in `task_day_counts`, which no client reads or writes, since a client sets `created_at` and can delete and add a task again. The tables that only grow have limits of their own: trips 5000, lodgings 5000, lodging_rooms 25000, lodging_prices 100000, quotes 100000, tasks 5000, task_log 5000 and agent_usage 10000. bookings, inbox and user_documents stay on the 2000 of `rows_per_private_table`. `queue_stay_details` catches only the cap's refusal around its task insert, so a lodging is added at the tasks cap without its stay_details task. A restrictive storage policy refuses a booking file that would take the caller's folder past `bookings_folder_bytes`. The admin is not exempt. The PC loop (`tasks.py`) and the cloud runner take the admin's tasks only: `tasks.py` adds `owner_id=eq.<owner>` to every query and exits when the owner is not the admin, the connector's claim and held-task reads add the caller's owner, and the wakeup of 0027 fires for the admin's tasks only. What other people add stays in their own rows and never reaches the shared catalogue.
- **Reasoning.** FEAT-006 lets other people use the same project through their own Claude, and PROD-008 keeps quotes private per owner. Policies in the database hold whichever client calls, so a bug in one client cannot read another person's data. Keys per owner let two people name a trip or a place the same. The fallback to the admin keeps the worker, the edge functions and the PC scripts working in the minutes between the release applying 0027 and their redeploy from the PC. A count readable by everyone is safe, a trip id is not. Old one folder booking paths stay readable to the admin through a temporary rule until `supabase/move_booking_files.py --apply` has moved them. A cap counts every row a person holds, so a table that only grows would stop the admin's worker or `save_trip` during the trip at 2000. Each table's own limit is the admin's live rows on 2026-11-06 plus 26 weeks at 3 times the rows added in the 7 days before, rounded up. trips held 36 and added 24 that week (1908 at 26 weeks), lodgings 38 and 38 (3002), lodging_rooms 255 and 255 (20145), lodging_prices 955 and 955 (75445), tasks 40 and 40 (3160) and task_log 36 and 36 (2844). quotes held 4223 and added 598 (50867), and the week before added 3625 in one crawl, so its limit also lasts 26 weeks at that rate (98473). agent_usage has no time column, so all its 96 rows count as one week (7584). Most of these rows came in during the move to Supabase in that week, so the week's growth is high and the limits err on the side of room. bookings held 10 and added 10 (790), inbox held none, and the 4 rows of user_documents are rewritten in place, so 2000 lasts for those three. The busiest day had 19 tasks, so 100 a day holds. A limit is one row of `owner_limits` and changes without a migration.
- **Applies to.** `supabase/migrations/0027_owners.sql`, `0028_bookings_bucket_folders.sql`, `0029_read_booking_cap.sql`, `0030_stay_prices_close.sql`, `0031_task_ids_per_owner.sql`, `0035_owner_caps.sql`, `supabase/tests/`, `supabase/move_booking_files.py`, `supabase/functions/stay-rates/`, `supabase/functions/read-booking/`, `plugin/scripts/tripdb.py`, `plugin/scripts/tripdb_store.py`, `infra/worker/`, `latam_trip_mcp/`, `planner/src/lib/`, `web/src/data/supabase.ts`, `data/README.md`.
- **Source.** `docs/product/features/FEAT-006-many-users.md` and `docs/superpowers/plans/2026-11-06-feat-006-many-users.md`, phase 2 and findings 3, 9, 11 and 12.
- **Date.** 2026-11-06. **Status.** Proposed.

## TECH-010 Supabase is the connector's OAuth server

- **Decision.** The connector stops being an authorization server and becomes a resource server only (way 1 of plan phase 3). Supabase Auth's OAuth 2.1 server signs people in, registers clients dynamically and issues the tokens. The connector's protected resource metadata names `https://<ref>.supabase.co/auth/v1` as its one authorization server and `scopes_supported: ["email"]`, since Supabase serves no custom scope and refuses `mcp`. A call without a valid token answers 401 with `resource_metadata`, and with `error="invalid_token"` when a token was given, so Claude refreshes. `oauth.verify_bearer` checks the signature against Supabase's JWKS, the issuer, aud `authenticated`, exp with no leeway, `role == authenticated` and a non-empty `client_id` claim, and returns `sub`. The key set is kept 10 minutes, and a token with an unknown `kid` fetches it again at most once a minute, so a withdrawn key stops working within 10 minutes and a flood of made up `kid`s cannot hammer Supabase. A planner session has no `client_id` and is refused. Each request builds its own `Core` on PostgREST with the publishable key as `apikey` and the person's token as bearer, so row level security (TECH-009) holds on every call and the connector holds no secret key. Migration 0033 makes the rest work as a person. `add_quotes` stays security invoker, is granted to `authenticated` and writes `owner_id` as `auth.uid()`, or the admin when the secret key calls, never from the payload. The airport codes a quote names must exist in the catalogue table `airports`, which only the admin writes, so `add_airport_stubs` is the one narrow security definer past it: it only inserts a missing code, never changes or deletes one, and for a person who is not the admin takes three capital letters and at most 200 codes a call. `stays` holds crawled prices with no owner, so it became a catalogue table, read by every signed in person and written by the admin. A flight change that gives a new quote id adds the new quote before it deletes the old one, and one that keeps the id puts the old quote back when the new one is refused. The function's role may read the two exact SSM parameters, the project URL and the publishable key, both plain String, and has no `kms:Decrypt`. The old secret key and passphrase parameters stay one day after the switch for a rollback. `deploy.sh --code-only` reads the function's configuration first and stops when `LATAMTRIP_URL_PARAM` or `LATAMTRIP_PUBLISHABLE_KEY_PARAM` is missing, so the release never ships this code to a function still configured for the secret key. The planner draws the consent page that Supabase sends the person to with an `authorization_id`. Its `authorization_url_path` is `/`, because the hosted planner is a bucket behind CloudFront that serves `index.html` at the root only, so the planner opens the consent page from the query and no infra changes. The connector serves no authorize, token, register or sign in route of its own, and the DynamoDB table keeps no login flow. It signs the person in if needed, leads with the planner's own mark, shows the client name with the redirect host under it and says what a connection can read and change, and refuses to approve a redirect host outside `claude.ai`, `localhost` and `127.0.0.1`. Approve and Deny post to `/auth/v1/oauth/authorizations/{id}/consent` and follow the answer's `redirect_url`. An authorization already approved answers with its `redirect_url` at once, and the page follows it. Every connect registers a new dynamic client, so the worker's `clients` action (`infra/worker/clients.py`) lists them with the admin OAuth clients API and deletes the dynamic ones made more than 30 days ago and unused for 30 days, at most 50 a run. When a client was last used is not in that API. It comes from the SQL function `oauth_client_last_used` over `auth.sessions`, which has no migration yet, so until it exists the action deletes nothing and is not scheduled. `secure_password_change` is on in the live project, because the connector token is a full session token. Two deviations are accepted. The token's aud is `authenticated` and not the connector URL, because Supabase ignores RFC 8707 `resource`, and the `client_id` check stands in for the audience check. The token passes through to PostgREST in the same project, which gains no privilege. A replayed stale refresh token is refused but does not revoke its family.
- **Reasoning.** The local spike (task 3.1) passed every graded part: discovery, dynamic registration, PKCE with consent, a token that is the person's and names the client, the connector verifying it against the JWKS and acting as the person, PostgREST returning only that person's rows, and refresh with rotation. Refresh after expiry passed on the local stack too: after 3604 s the connector refused the expired token with 401, the refresh answered 200, and the connector answered 200 with the new token. PostgREST still accepts a token up to 30 s past exp, its fixed clock skew allowance, so the connector's own exp check with no leeway is what makes Claude refresh, and that check keeps zero leeway. A security definer function was weighed against granting authenticated insert on `airports`. The function keeps the catalogue admin written and lets a person add nothing but a missing three letter code. Way 2, tokens minted by the connector, would bring back a signing key and an authorization server to keep, for an audience claim that PostgREST does not check. Way 1 removes the secret key and the DynamoDB login flows from the connector. Dynamic registration takes any client name and any redirect host, so the redirect host check on the consent page is what stops someone approving another person's link to a foreign host. Discovery on the hosted project was the one open risk, because locally only `/auth/v1/.well-known/openid-configuration` answers. On 2026-11-06, with the OAuth server turned on in the live project, `/.well-known/oauth-authorization-server/auth/v1`, `/auth/v1/.well-known/oauth-authorization-server` and `/auth/v1/.well-known/openid-configuration` all answer 200 with the issuer `https://<ref>.supabase.co/auth/v1`, so a client that follows RFC 8414 or the MCP order finds it. Phase 7 still checks it end to end with claude.ai as the client.
- **Sign up by invite (task 6.1).** Sign up is on in the project and gated by the Postgres hook `before_user_created`, `public.hook_before_user_created` of migration 0036, which refuses an address with no unused row in `invites` with a 403 "Sign up is by invite only" and marks the invite used. Only `supabase_auth_admin` may run it, and no client reads or writes `invites`. The admin adds invites with `tripdb invite EMAIL` on the secret key. Supabase calls the hook only when a sign up or an email link would make a new user, so everyone who has an account signs in as before, and a user made with the admin API skips it. The hook runs outside the transaction that makes the user, so a link that fails to send after it leaves the invite used, and `tripdb invite` opens it again. The planner has one way in for everyone, the email link with `shouldCreateUser` on, and shows a refusal as the invite state on the address itself. That state tells only that the address has neither an account nor an open invite, the same for an address never invited and one whose invite is used. A Postgres hook was chosen over an HTTP hook because it needs no function to deploy and reads the table in the same database. Turning the hook off opens sign up to everyone with no change to any row. Turning sign up on also opens email and password sign up at `/auth/v1/signup` to anyone with the public publishable key, so someone who knows an invited address could sign up first with a password of their own. Two things close that. Confirm email must stay on in the project (`mailer_autoconfirm` false), so such a sign up gets no session until the address is confirmed by its email link, which only the invitee receives. And the trigger `clear_signup_password` of 0036 clears the password of every user a client sign up makes, so that password never signs in, before or after the invitee confirms the address. Supabase Auth inserts the same row for a client sign up and for the admin API, which confirms the address in a second step, so the trigger tells them apart by the invite the hook has just marked used. A user made with the admin API has no used invite and keeps its password, which the database tests and scripts rely on. The planner signs in by email link only, so no person loses anything. The local stack runs with confirm email on as well (`enable_confirmations` in `config.toml`).

## TECH-012 Realtime on a private topic per owner

- **Decision.** Migration 0034 takes the private tables out of the `supabase_realtime` publication (trips, bookings, lodgings, lodging_rooms, lodging_prices and tasks, the ones that were in it). Statement level triggers on those six tables call `realtime.send` once per owner a statement touched, on the private broadcast topic `owner:<user id>`, with the table's name as the event and `{"op": "insert" | "update" | "delete"}` as the whole message. No column of the row goes into `realtime.messages`. The trigger function `public.tell_owners` is security definer, so it writes the message whoever made the change, the secret key included. One policy on `realtime.messages` lets an authenticated person read, and so join, only the topic `owner:` plus their own id. No policy lets a client send, so only the triggers write to a topic. The planner holds one private channel per tab for the signed in person (`planner/src/lib/ownerFeed.ts`), moves it on a sign in or sign out, and hands each message to the listeners of that table, which read the rows again as they did on a Postgres Changes event. A message sent while the channel is away is lost, so on every join after the first each listener reads its rows again, and a failed join is logged with its status only, since the error's text names the topic and so the user id. `derive_state` is shared, holds no private data and stays on Postgres Changes. The web map listens to no private table.
- **Reasoning.** Postgres Changes does not apply row level security to a delete, so every subscriber heard the old row's primary key, which carries the owner's user id and for trips the trip name. Leaving the publication alone would have ended live updates. The planner already threw the event's payload away and read the rows again, so a broadcast that names only the table keeps it live with nothing of the row in the message. `realtime.broadcast_changes` was weighed and not chosen, because it puts the old and new row into `realtime.messages`, which would leave the private data in one more table whose policy must hold. A topic per owner with row level security on its join is how Supabase scopes a broadcast, and one message per owner and statement keeps a batch of prices to one message. A person learns only that one of their own tables changed.
- **Applies to.** `supabase/migrations/0034_owner_realtime.sql`, `realtime.messages` policies, `planner/src/lib/ownerFeed.ts`, `planner/src/lib/bookings.ts`, `lodgings.ts`, `remoteTrips.ts`, `tasks.ts`, `supabase/tests/test_rls.py`, `data/README.md`. The hosted project keeps Realtime's public channels allowed, since `derive_state` still uses one.
