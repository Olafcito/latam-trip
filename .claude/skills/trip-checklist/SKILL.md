# Trip checklist

For the always on mode, where a cheap dispatcher waits on the queue and sends one subagent per task, use the `task-loop` skill.

The app writes tasks and you do them. The contract and task types are in `docs/claude-tasks.md`, read it first. Data lives in Supabase (see `data/README.md`). Read a table with `tripdb query TABLE` (for example `quotes`, `experiences`, `tasks`, `task_log`, `places`, `connections`) and a built file with `tripdb file NAME`. Flights are in `quotes`. Prices of places to stay are written through the latam-trip connector with `add_lodging_price`. The rooms, room photos and place photos of a Booking.com place go through `tripdb lodging-details`. Every other write goes through tripdb (`python -I -X utf8 plugin/scripts/tripdb.py --root . <command>`), never by hand.

## Rules (Simon's, always)
- Never book, reserve, pay, sign in, enter personal data, accept consent or solve a bot check. Search and read only.
- Browser work goes to Sonnet subagents only (never Haiku), at most 2 browser workers at once. Momondo is the main flight engine.
- Connectors: the Booking.com connector, for beds (`accommodations_search`) and, in experience research, things to do (`attractions_search`), and the latam-trip connector, to read places to stay with `list_lodging` and `get_lodging` and write their prices with `add_lodging_price`. No other connector, except the Chrome plugin for `stay_details` when the headless read is blocked.
- Long-haul is never searched one-way alone: any leg touching Europe is searched as one combined ticket from and back to Copenhagen (CPH), with the rest of the trip as fixed in the `trip.json` document (`tripdb doc-get trip.json`). More than 30 h in one direction is unacceptable.
- Results always give local departure and arrival clock times, one fact per cell, kroner (DKK). No em or en dashes. No route suggestions unless the task asks.

## Steps
1. `python3 -I plugin/skills/trip-checklist/scripts/tasks.py list` (or use the pasted task JSON). Run `show N` for each, and `start N` when you begin it. Group tasks of the same kind so one worker batch covers several (about 8 searches per worker).
2. Per type:
   - `flight_prices`: follow the `flight-crawl-orchestrator` skill. Write a task list for `agents/momondo-worker.md` (one search per task, legs and dates from the task, each leg's `flex_days` as neighbouring dates, and `all_flights` when the task has it: then the worker follows its All flights section and every date counts as a search in the batch). A self-built itinerary is searched three ways (see `docs/claude-tasks.md`): legs touching Europe as one combined ticket, regional legs as one-ways, and the whole as one multi-city search if it has 6 legs or fewer. After the RESULT the worker has run `tripdb add-quotes`.
   - `stay_prices`: the task names a lodging that exists (`lodging_id`), the rooms to price (`room_ids`) and the dates. Dispatch `agents/stay-price-worker.md` with the task id, `lodging_id`, `room_ids`, `check_in` and `check_out`. The worker reads the lodging with the connector's `get_lodging` and writes one `lodging_prices` row per room with `add_lodging_price`. If it could not, add its rows from `data/raw/stays-<agent>.jsonl` with `add_lodging_price` yourself. Hostelworld rooms are priced by the `stay-rates` edge function, so the worker prices Booking.com unless a Hostelworld room has no price. A price task writes prices only: never add a lodging or a room for it, and never write the old `stays` table (`tripdb add-stays` is closed). A task without `lodging_id` and `room_ids` is from before places to stay: close it with a result that says to ask again from the lodging in the app.
   - `stay_search` and `stay_picks`: the task runner normally takes them. When you meet one, follow the `task-runner` skill's contract for it (`claim_task` gives it): Booking.com's best rated places at the stored `place_id` for the dates, added with `add_lodging`. The Hostelworld half is the `stay-rates` edge function's job.
   - `stay_details`: the task names a Booking.com place (`lodging_id`). It is not a cloud task, so it is done here on the PC. Dates are the task's `check_in` and `check_out`, else the dates of the lodging's latest price, else the dates in its Booking.com link, else none (rooms and photos only). `read.mjs` falls back the same way when no dates are given. Run `node plugin/scripts/booking/read.mjs LODGING_ID [--check-in YYYY-MM-DD --check-out YYYY-MM-DD] --out FILE` (setup once with `npm install` in `plugin/scripts/booking`), then `python -I -X utf8 plugin/scripts/tripdb.py --root . lodging-details FILE` (add `--dry` to look first), then `tasks.py done`. If the headless read is blocked, dispatch a Sonnet subagent to read the same page in Simon's Chrome through the Chrome plugin and write the same JSON. Read only: never click a consent, sign in or solve a bot check.
   - `experience_research`: research it yourself with WebSearch and WebFetch, and the Booking.com connector's `attractions_search` for bookable tours and tickets (prices, season, Dec/Jan conditions, requirements, how to book, 2 to 4 sources). Add a row with `python -I -X utf8 plugin/scripts/tripdb.py --root . add-experience FILE` or change one with `python -I -X utf8 plugin/scripts/tripdb.py --root . update-experience ID --set field=value` (schema below), set `researched: true` and `checked_at`. New experiences get a category from `experience_categories.json`.
   - `place_research`: dispatch `agents/network-researcher.md` and `agents/place-profiler.md` for the new place (they add it with tripdb add-place, add-connection and add-profile).
   - `lists_update`: `python -I -X utf8 plugin/scripts/tripdb.py --root . list-add LIST place|experience ID [--note TEXT]` or `list-remove LIST place|experience ID` (it sets `added` to today and keeps notes).
   - `question`: answer in the result of the task.
   - `refresh`: list what is in scope and older than `older_than_days`. For flights that is `observed_at` from `tripdb query quotes`, using `--in build_qid=...` for the tickets of the top 10 trips in `tripdb file dash_trips.json`, their long-haul tickets and regional pairs, and every `flight_prices` itinerary in `tripdb query task_log`. For stays it is the rooms and dates of the latest prices of each lodging from `list_lodging` and `get_lodging`, priced again into `lodging_prices` as a `stay_prices` task would. For experiences it is `checked_at` of researched rows. Re-run those as the tasks above would, in as few worker batches as possible. Tell Simon the size first if it is more than 4 worker jobs.
3. Write a short result (markdown table: what was found, prices, local times, sources) to a file and run `python3 -I plugin/skills/trip-checklist/scripts/tasks.py done N <file> --outputs <files changed>`. That stores it as the result, marks the task done, so the app shows it, and logs it with `tripdb log-task`.
4. Nothing to rebuild or publish. The worker rebuilds the app files within 1 to 3 minutes. If you changed anything under plugin/, run `python -I plugin/scripts/sync_claude_dir.py --root .`, commit and push.
5. Tell Simon in a few lines what was done, with the key prices, and anything blocked.

## Momondo save tasks
Tasks from the Momondo userscript (docs/momondo-save.md) arrive in the tasks table as `fix_parser`. Saved prices go straight to the inbox table and the worker ingests them on its next run. Run `node plugin/skills/momondo-search/scripts/canary.js` first, and `canary_live.js` when a browser is available.
- `fix_parser`: save `dialog_text` as a new fixture in `plugin/skills/momondo-search/scripts/fixtures/`, reproduce the failure with `parseDlg` from `momondo_crawler.js`, fix the parser and bump `PARSER_VERSION`. Add the `.expected.json` for the fixture, run `node plugin/userscripts/build.js` and `node --test "plugin/userscripts/**/*.test.js"`, push, then close the task with `tasks.py done` and the new parser version in the summary.
- `import_quotes`: only filed by hand. Write `rows` unchanged to the inbox table with a row of status `new`, then close the task with the number of rows added.

## Experience row (the experiences table, one JSON object per row)
`{"kind": "experience", "id": "kebab-id", "name": "...", "category": "<category id>", "tags": [], "places": ["<map ids>"], "area": "<name when no map place>", "country": "XX", "lat": 0.0, "lon": 0.0, "summary": "...", "season": "...", "dec_jan": "...", "price": "as published", "price_dkk": 0, "duration": "...", "requirements": "...", "details": {}, "researched": true, "checked_at": "YYYY-MM-DD", "sources": ["..."]}`
Category-specific facts go in `details` (diving: water, animals, shark_chance, depth, cert, logged_dives_min). Images: an `experience_image` row added with `tripdb add-experience-image FILE` (`{"kind": "experience_image", "id": ..., "image": {url, page, credit, license, w, h}}`), Wikimedia Commons, free licence, no identifiable people.
